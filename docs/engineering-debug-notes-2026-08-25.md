# 地图工作台工程难点与解决记录

日期：2026-08-25

本文记录本轮地图工作台改造、调试和验证中遇到的主要难点、根因、处理方式和剩余风险。文档不包含 API key、数据库密码或其他敏感配置。

## 1. 任务完成后页面没有反馈

### 现象

- 用户提交制图请求后，页面可能长时间停留在“待连接”或没有明显进度。
- 后端任务失败时，前端可能看起来像一直等待。

### 根因

- 前端依赖 SSE 和轮询共同获取状态，但旧连接、重连游标和新任务事件之间存在竞态。
- 任务提交失败时，如果只启动后台任务而不持久化提交异常，`MapRequest` 或运行记录可能停在处理中。
- 页面只展示最终结果，缺少启动、处理中、失败和等待补充信息等明确状态。

### 处理

- 引入 `MapRun` 运行记录，记录 pending、running、awaiting_input、completed、failed 等状态和时间信息。
- SSE 生命周期事件携带可继续消费的游标，前端提交新任务后从新游标开始监听，避免旧事件覆盖新状态。
- worker 入队异常立即持久化为失败，写入 `result_message`、错误日志和助手消息，并通过 SSE 通知页面。
- 前端在任务开始后立即切换为“生成中”，禁用重复提交按钮；失败时展示可读错误和下一步提示。

## 2. 第一次能生成，第二次调整没有反应或结果不变

### 现象

- 第一次地图创建成功后，第二次输入“标注清华大学的位置”等调整请求，页面没有动作，或者 v2 看起来与 v1 一样。

### 根因

- 第二次任务仍沿用旧 SSE 连接或旧游标，导致新事件没有被当前页面消费。
- 连续请求没有统一的运行锁和重复提交保护，存在旧任务回写新状态的风险。
- 只检查“任务完成”不足以证明地图真的变化，必须检查版本和生成文件内容。

### 处理

- 连续调整使用独立的 `MapRun` 和新的 SSE 起始游标。
- 对创建和调整请求增加提交锁、运行状态保护及旧连接竞态处理。
- 调整成功后读取生成地图列表，确认同时存在 v1、v2。
- E2E 测试对 v1、v2 PNG 计算 SHA-256，确保两版文件内容确实不同，而不是重复返回旧图。

## 3. 后台 worker 失败后任务永久处于处理中

### 现象

- Redis、Celery worker 或任务提交过程发生异常时，用户只能看到等待状态。

### 根因

- 任务提交和任务执行是两个阶段，提交阶段抛出的异常之前没有完整写入业务状态。
- 仅依赖线程或 Celery 的日志，页面和 REST 状态无法得知提交失败。

### 处理

- 新增统一的 dispatch failure 处理：更新 `MapRequest` 为 failed，更新 `MapRun`，写入 `ProcessLog` 和 `ChatMessage`，发布 `request_failed` 与 `done` 事件。
- worker 执行异常也会写入 `result_message` 和 `error_message`，避免用户只看到空白结果。
- Docker Compose 使用 Redis 作为 Celery broker，web 和 worker 分离运行，并在启动后检查 worker ready 日志。

## 4. 模糊、片段化或信息不足的输入

### 现象

- 用户输入“帮我画个图”“北京”“改一下”等低信息需求时，系统容易过度假设，或者没有告诉用户需要补充什么。
- 用户补充信息后，系统需要保留前面已经说过的内容。

### 根因

- 过去的规则兜底倾向于在无法判断时默认 create 或 modify。
- 澄清结果没有独立状态，前端无法区分“处理中”和“等待用户补充”。
- 只把最后一轮文本传给 Agent，会丢失用户前面的上下文。

### 处理

- 增加 ambiguity detection：识别缺少区域、图层类型、目标对象或修改动作的请求。
- 增加 `needs_clarification` 响应和 `MapRun.STATUS_AWAITING_INPUT`，页面展示澄清问题、缺失字段、建议示例和下一步动作。
- 模糊输入不再默认猜测 create/modify，规则兜底返回 clarification。
- 澄清重试时将历史用户轮次和最新补充信息组合后传给 Agent，并保留原始消息记录。

## 5. “生成成功”不等于地图正确

### 现象

- 文件可以生成，但数据范围、数据集语义、图层几何类型或地图内容可能不符合用户说的城市和主题。
- 例如名称包含道路的请求，不能只凭 PNG 存在就判断是正确的道路地图。

### 根因

- 传统制图工具和 LLM 意图识别解决的是“能否执行”，不自动保证数据源语义正确。
- 本地数据目录可能存在命名宽泛、数据内容不完整或几何类型与名称不一致的文件。

### 处理

- 增加数据集目录、别名、几何类型、范围、要素数量和来源元数据的管理接口。
- 通过数据源选择层优先匹配区域、主题和几何类型，不能匹配时返回澄清或明确失败。
- E2E 不只检查状态，还检查生成版本、文件存在性、文件大小、哈希差异和页面错误。

### 剩余风险

- 当前仍需要继续完善数据质量校验：应在任务完成前校验图层主题、几何类型、空间范围和要素数量，并在不符合用户意图时阻止“成功”状态。

## 6. 前后端地图状态和渲染结果不一致

### 现象

- 后端生成了 PNG，但前端实时图、历史图或当前地图状态可能不是同一个版本。
- 大数据图层如果直接一次性加载 GeoJSON，会影响页面响应。

### 根因

- PNG 文件、地图状态快照和前端 OpenLayers 图层是不同表示，缺少统一的版本和图层清单。
- 大数据解析和渲染放在主线程会阻塞交互。

### 处理

- 以地图快照和图层 manifest 作为前后端共享契约，前端根据版本读取当前状态。
- 增加 GeoJSON 解析 worker、图层注册表、渲染策略和数据加载器；大数据路径预留 MVT/分块加载能力。
- 前端地图交互区域允许平移和滚动，避免固定容器遮挡地图内容。

## 7. Trace 缺失导致无法定位一次运行

### 现象

- 第二次调整可以拿到 `trace_id`，但首次创建完成后 REST 返回的 `latest_run.trace_id` 为空。

### 根因

- Agent 某些创建路径没有返回 `tool_trace_id`，而运行记录只在收到 Agent 返回值后才尝试写入。

### 处理

- 在任务入队时先写入稳定的默认 trace：
  - 创建：`web_session_<request_id>:create`
  - 连续调整：`web_session_<request_id>:conversation`
- 如果 Agent 返回更具体的 trace，后台完成阶段覆盖默认值，例如 `web_session_114:modify_map`。
- 增加回归测试，确保任务尚未执行时也已有可追踪标识。

## 8. Docker、外部服务和启动时序

### 现象

- Docker 引擎或容器重启后，立即运行浏览器脚本可能找不到登录页元素。
- Redis、PostGIS、Neo4j、web、worker、nginx 启动时间不同。

### 处理

- Compose 中为 Redis、PostGIS、Neo4j 配置健康检查，并让 web/worker 依赖健康状态。
- 浏览器 E2E 在登录前先等待 HTTP 登录页返回 200，再等待页面网络空闲。
- 应用重启时只重启 web、worker、nginx，数据库服务保持运行，减少数据服务中断。
- 运行数据和生成文件放在项目目录的 runtime/、outputs/、generated_maps/ 等目录，不写入 C 盘。
