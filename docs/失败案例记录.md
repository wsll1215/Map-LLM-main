# 地图制图失败案例记录

最后更新：2026-08-30

本文是地图制图系统的持续失败案例台账。记录目标不是只记录异常文本，而是把“用户需求 -> 调用链 -> 失败位置 -> 根因 -> 修复 -> 回归结果”串起来，防止同一类问题反复出现。

## 记录规则

1. 每次自动化测试失败、浏览器验收失败，或用户反馈“没有反应、结果不对、图层缺失、页面显示错误”，都必须追加一条案例；不能只在聊天中说明。
2. 优先从 `MapRequest`、`MapRun`、`ProcessLog`、Trace、SSE/浏览器报告中取证。没有真实 trace 时写明“未采集”，不得编造。
3. 同一根因再次出现时，不新建模糊的重复描述；在“重复次数”中增加计数，并列出新的 request id/trace。
4. “任务完成”不等于“案例成功”。地图范围、图层语义、图层数量、数据来源和 PNG 内容都必须符合需求，才可以标记为已修复。
5. 每条案例必须填写：失败需求、来源、request id、trace、失败位置、根因、解决方式、解决结果、同类问题此前出现次数和回归证据。
6. 运行产物放在项目目录下的 `outputs/`、`tmp/` 或 `data_cache/`，文档中只引用路径，不写入 API key、密码或其他敏感信息。

## 状态定义

- `待定位`：已有失败证据，但根因尚未确认。
- `已定位`：根因已通过日志、代码或数据对照确认。
- `修复待回归`：已修改代码，但还没有完成对应验收。
- `已修复`：修复后有自动化测试或真实浏览器验收证据。
- `重复回归`：已经修复过的根因再次出现，需要重新处理。

### INTENT-001-20260830-153：自然语言地点未被识别，提前阻断远程数据链路

- **来源**：用户真实测试 + Trace。
- **失败需求**：`给我天津市的地图，并且要有道路跟河流`。
- **request id / run id / trace**：`153 / 207 / web_session_153:create`。
- **任务状态**：意图解析阶段产生错误成功；后续应进入 `needs_clarification`，未进入远程数据源规划。
- **失败位置**：`gis_mapping_agent/data_sources/planner.py` 的 `parse_intent()` -> `_extract_intent_location()`。
- **证据**：Trace `event_seq=10` 的 `intent_parse` 状态为 `success`，但 `output.location.text=null`、`precision=null`、`confidence=0.25`；道路和河流仍被识别为必需图层。
- **背后 bug**：地点提取正则的动作词集合不包含“给我”。`planner.py` 因此无法从“给我天津市的地图”提取地点；而 `remote.py` 的另一套 `extract_location_query()` 已支持“给我”，两套规则不一致。同一语义在不同阶段会得到不同解析结果。
- **哪里出错**：`parse_intent()` 只以“函数没有抛异常”将事件标为 `success`，没有按 Intent 契约校验地点是否为空、置信度是否足以继续；`unknown_fields` 也没有记录地点未识别。
- **影响**：`thinking.py` 在调用 `build_source_plan()` 前命中 `intent.layers and not intent.location.text`，直接返回 `clarification_required`，所以本次没有调用 Nominatim、Overpass，也不会产生道路和河流远程图层。不是远程数据库拒绝或缓存缺失。
- **解决方式**：待实施。统一地点解析入口和动作词/语义规则；对带必需图层但地点为空或置信度不足的 Intent 标记结构化 `clarification_required`，并在 Trace 中明确“地点提取失败”，禁止将其标记为语义成功；补充同义表达变形测试。
- **解决结果**：已定位，未修复。
- **同类问题此前出现次数**：1 次已确认的地点/远程链路提取类问题（`BC-20260825-132`）；本条是规则不一致导致的独立回归。
- **回归证据**：已采集真实 Trace；修复后需验证“给我/请/帮我/绘制/显示”等表达生成等价 Intent，并确认后续出现 `source_plan` 和远程数据事件。

### PERF-001-20260828：Worker 低规模交互变慢，MVT 旧基准异常变慢

- **来源**：自动化浏览器 A/B 性能复测 + 代码审查
- **失败需求**：按固定阈值验证主线程 GeoJSON、Worker GeoJSON、MVT 的性能优化；发现 Worker 降低 Long Task 但部分交互时间变慢，MVT 旧报告明显慢于基线。
- **request id / trace**：性能基准无业务 request；trace 未采集，使用 `tests/performance/` 的场景和样本证据。
- **任务状态**：已定位；Worker 5001 的负向结果保留为真实边界结果，MVT 旧负向结果已修正。
- **失败位置**：前端批次调度、OpenLayers 重绘调用、MVT 基准瓦片粒度和正确性口径。
- **证据**：`docs/performance/negative-optimization-analysis.md`；正式报告 `docs/performance/render-ab-report-after-scheduler.md`；原始数据 `tests/performance/observations-final-after-scheduler.json`；7 个规模、14 个 A/B 组、420 条样本，每组 30 条。
- **背后 bug**：Worker 批次每次显式 `map.render()` 造成重复绘制；旧 MVT 基准使用不匹配的瓦片粒度并集中生成巨型瓦片；同时 `interactive_ms` 的含义没有和“主线程不被长任务阻塞”区分。
- **哪里出错**：`frontend/src/hooks/useOpenLayersMap.ts`、`frontend/src/benchmark/benchmark.ts`、`frontend/src/map/renderers.ts`、`tests/performance/run_render_ab.py`。
- **解决方式**：移除重复 `map.render()`；首批使用 rAF，后续批次使用带 100ms 超时的 `requestIdleCallback`，不支持时回退到 rAF；MVT 使用 256px tile grid，基准使用 z11 可见瓦片分布，并显式记录 `correctness_scope=visible_tiles`。
- **解决结果**：正式实验确认 MVT 交互 median 降低 73.5%，Long Task 降低 69.5%；Worker 在 10000、29999、30000 的交互 median 分别降低 15.8%、43.9%、40.5%，但 5001 仍因 Worker 固定成本上升 17.1%，作为真实 trade-off 保留，不能标记为全面加速。
- **同类问题此前出现次数**：1 次确认（此前旧报告曾把负向结果记录为异常，但未区分实现问题和测试口径）。
- **回归证据**：正式 A/B 420/420 条样本正确性通过；`npm run test -- --run` 109/109；`npm run build` 通过；后端定向测试 81/81；全量 `pytest -q` 342/342；`python manage.py check` 通过。

### BC-20260825-132：定州市地图使用了错误的本地道路，且没有小学

- **来源**：用户反馈 + 真实数据库/ProcessLog 核验。
- **失败需求**：`帮我绘制定州市地图，标注主要道路和小学，并在页面显示每个图层的数据来源。`
- **request id**：`132`
- **trace**：`web_session_132:create`
- **任务状态**：数据库显示 `completed`，但业务结果实际不合格，应视为错误成功。
- **失败位置**：远程边界解析和数据源规划阶段。
- **证据**：
  - ProcessLog `2726`：远程地理编码查询为 `定州市地图，标注主要道路和`，未返回边界。
  - ProcessLog `2730-2731`：使用全球默认范围 `[-180, -90, 180, 90]`。
  - ProcessLog `2739`：只添加了 `本地道路`，7 个要素。
  - 状态库图层：`data/data1/Highway.shp`，范围 `109.74~117.08E，20.27~25.34N`，与定州市约 `38.5N` 不符。
  - 状态库没有小学图层；`data_cache/` 没有本次生成的 `remote_pois` 缓存。
- **背后 bug**：`extract_remote_poi_request()` 在组合需求中把 `定州市地图，标注主要道路和` 当成地点；边界失败后错误地继续使用未做空间匹配的 `data/data1/Highway.shp`。道路和小学的 Overpass 调用依赖边界 bbox，因此没有被调用。
- **哪里出错**：`gis_mapping_agent/agent/thinking.py` 的地点选择和远程数据准备；`gis_mapping_agent/data_sources/remote.py` 的组合语句地点提取；完成判定没有检查请求的图层是否全部存在。
- **解决方式**：
  1. 优先使用通用地点解析结果，清洗为 `定州市`。
  2. 本地数据必须通过地点 bbox、几何类型和主题校验，空间不匹配时拒绝使用。
  3. 边界成功后分别调用 Overpass 道路和小学，并记录来源、bbox、要素数和缓存路径。
  4. 具体城市请求禁止使用全球默认范围。
  5. 请求的任一必需图层缺失时禁止标记 `completed`。
- **解决结果**：未修复。当前只完成定位，代码和 `#132` 数据尚未重新生成。
- **同类问题此前出现次数**：至少 1 次已确认（广东省旧案例）；同类“远程数据缺失/本地源不匹配”在 #115、#116、#121、#122、#125、#127、#129 中至少出现 7 次。
- **回归证据**：待补充。修复后必须重新测试本需求，并确认道路、小学两个图层和定州空间范围。

### BC-20260825-FLOW：第二次调整没有反应或 v2 与 v1 相同

- **来源**：用户多次反馈 + 浏览器回归测试。
- **失败需求**：第一次生成地图后，再输入“标注清华大学的位置”等第二个需求。

- **同类问题此前出现次数**：至少 2 次用户反馈，另有 1 组浏览器回归复现。
- **回归证据**：`docs/engineering-debug-notes-2026-08-25.md`、`outputs/manual_second_request_e2e.png`。

### BC-20260825-FEEDBACK：失败或处理中页面没有明确反馈

- **来源**：用户反馈、早期浏览器验收。
- **失败需求**：各种制图请求在 worker、Redis、SSE 或远程数据失败时，页面应立即说明状态。
- **request id / trace**：不同历史任务混合出现，部分旧任务没有 trace；后续新任务使用 `web_session_<request_id>:create`。
- **失败现象**：页面停留“待连接”、没有中间进度、失败后用户只能等待，或任务显示完成但没有可用成果。
- **背后 bug**：任务提交、worker 执行、SSE 连接和前端轮询之间缺少统一状态；异常没有完整持久化。
- **解决方式**：增加 `MapRun` 状态、ProcessLog、ChatMessage、SSE 生命周期事件和前端失败卡片；Redis 不可用时走状态轮询并显示降级信息。
- **解决结果**：主要流程已修复，仍需在远程服务故障和 Redis 断开场景持续回归。
- **同类问题此前出现次数**：多次，准确次数未从旧日志中统计。
- **回归证据**：`docs/engineering-debug-notes-2026-08-25.md`、`outputs/e2e/` 下的浏览器报告。

### BC-20260825-UI：历史记录过长无法快速到达底部、文字溢出

- **来源**：用户截图反馈。
- **失败需求**：历史记录很多时，用户应能快速查看最新记录；按钮、来源标签和状态文本应完整显示。
